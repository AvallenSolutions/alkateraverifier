## Build Philosophy

1. **Each phase ships something usable.** No phase leaves the app broken. After any phase, you can demo what you've built.
2. **Infrastructure before features.** Phase 0 sets up everything so feature work later is fast and clean.
3. **Magic moment first.** The core value (upload → select standards → transparent verdict in minutes) works by the end of Phase 2. Everything else builds on top.
4. **Test as you go.** The extraction and rules layers carry a fixtures-based test suite from the moment they exist. Don't defer testing.
5. **Progressive enhancement.** Start with the simplest working version, then layer on polish.
6. **Review before proceeding.** Push each completed phase as a PR and let a review agent (e.g. [CodeRabbit](https://coderabbit.ai)) review it before starting the next phase.
7. **Never assert without a citation.** Every finding the engine produces must cite a standard and clause, or be marked `insufficient_info`. This is the product's core promise and a build-time invariant.
8. **Fail honestly, cheaply.** Keep per-verification Claude cost low, and never emit a false pass; an "insufficient information" state is always preferable to a wrong verdict.

## Agent Session Guide

### How to Use This Roadmap with Your Coding Agent

1. **Start a session:** Give your coding agent the phase prompt at the beginning of each phase.
2. **Read selectively:** Each phase lists its Reference sections, the specific parts of the PRD and vision doc needed. Read only those, not the entire documents.
3. **Let it work:** The agent finds the first unchecked task, implements it, and marks it complete.
4. **One session = one phase (ideally):** Complete a full phase per session for continuity. To stop, resume from the last unchecked task.
5. **Push a PR for review:** When a phase is complete, push a PR and let a review agent (e.g. [CodeRabbit](https://coderabbit.ai)) review before starting the next phase.
6. **Need more context?** If a task references a section not in the phase's Reference sections, read just that section on demand.

### Session Tips

- **Don't read everything:** Each phase's Reference sections tell the agent exactly what to read. Loading full docs wastes context.
- **Don't skip tasks:** Tasks are ordered intentionally; skipping creates dependency issues.
- **Verify after each phase:** Run the app after each phase before moving on.
- **Review before moving on:** Push a PR per phase; don't start the next until it's merged.
- **Update the status line:** After completing tasks, update the header: `**Status:** X/58 tasks complete` and `**Current Phase:** Phase N`.
- **Database migrations:** Post the full SQL of every migration in chat so Tim can run it in the Supabase SQL editor.
- **Run the Design System skill** before Phase 1 styling work so `docs/design.md` exists; until then use neutral placeholder tokens.

> "There's a problem with [description]. Read the relevant section of docs/prd.md for the expected behavior and fix it. Don't mark any new tasks complete until the fix is verified."

### Phase Review Workflow

After each phase, push the work as a pull request and let an automated review agent ([CodeRabbit](https://coderabbit.ai) recommended) review before merging. Address feedback in follow-up commits on the same branch, re-review, and merge only when clean. If you are not using GitHub PR review, you lose automated detection of bugs, security issues, and style problems the coding agent may miss; per-task verification still applies.
